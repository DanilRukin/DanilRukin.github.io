# DDD в Legacy проекте: От хаоса к порядку

## 🏗 Контекст проекта

**Проект:** ERP система для энергетической компании  
**Возраст:** 15+ лет разработки  
**Команда:** 10 человек (2 mid, 3 junior, 2 qa, 2 аналитика, 1 техническая поддержка)  
**Технологии:** .NET Framework 4.5.2, WPF, WCF, SQL Server 2016  
**Размер:** SQL 685k+ строк кода, C# 280k+ строк кода, XML 370к+ строк кода, 1500+ таблиц в БД

### **Проблемы, которые мы имели:**

1. **Непонятная бизнес-логика**

   - Бизнес-правила размазаны по UI, бизнес-логике и БД
   - Магические числа и строки по всему коду
   - Отсутствие единого языка

2. **Архитектурный хаос**

   - "Божественнык классы" (5000+ строк)
   - Смешивание ответсвенностей разных слоев приложения
   - Анемичная модель предметной области
   - Сложные хранимые процедуры/функции с бизнес-логикой

3. **Процессные проблемы**

   - Высокий порог входа (6+ месяцев для нового разработчика)
   - Страх изменений (каждое изменение ломает что-то неожиданное)
   - Некачественное code-review или его отсутствие
   - Частые production инциденты

4. **Бизнес-проблемы**
   - Медленная разработка новых функций
   - Высокая стоимость изменений
   - Невозможность масштабирования команды

## 🎯 Почему выбрали DDD?

### **Альтернативы и почему их отклонили:**

1. **Просто продолжить как есть**

   - ❌ Проблемы только усугубляются
   - ❌ Команда демотивирована
   - ❌ Бизнес недоволен скоростью

2. **Взять и все переписать с нуля**

   - ❌ Слишком рискованно
   - ❌ Бизнес не даст 1-2 года без новых фич
   - ❌ Нет гарантий успеха

3. **Архитектурные подходы (Clean Architecture)**

   - ✅ Хорошие подходы, но...
   - ❌ Не решают проблему _единого языка_
   - ❌ Не фокусируются на _домене_

4. **DDD (Domain-Driven Design)**
   - ✅ Решает проблему единого языка
   - ✅ Фокус на бизнес-домене
   - ✅ Подходит для сложных domain
   - ✅ Можно внедрять постепенно

## 🚀 Наш подход: Стратегия Strangler Fig

Мы выбрали **Strangler Fig Pattern** - постепенное замещение legacy кода новыми компонентами.

# **Фаза 1: Подготовка (2 месяца)**

## 1.1 Обучение команды

- Провели 4 воркшопа по DDD (по 4 часа каждый)
- Темы: Ubiquitous Language, Bounded Contexts, Entities/Value Objects
- Практические упражнения на нашем коде

## 1.2 Создание глоссария

# Energy Billing Domain - Ubiquitous Language

## Core Concepts

### Customer (Клиент)

- **Definition:** Лицо или организация, потребляющая энергоресурсы
- **Attributes:** account_number, full_name, address, tariff_plan
- **Business Rules:** Must have unique account_number

### Meter (Счетчик)

- **Definition:** Устройство для измерения потребления энергоресурсов
- **Attributes:** serial_number, installation_date, meter_type
- **Business Rules:** Can be associated with only one Customer

### Reading (Показание)

- **Definition:** Значение, снятое со счетчика в конкретный момент времени
- **Attributes:** value, reading_date, meter_id
- **Business Rules:** Value must be >= previous reading

### Invoice (Счет)

- **Definition:** Документ с суммой к оплате за период
- **Attributes:** invoice_number, amount, due_date, status
- **Business Rules:** Can be in statuses: draft, issued, paid, overdue

### Payment (Платеж)

- **Definition:** Оплата счета клиентом
- **Attributes:** amount, payment_date, payment_method
- **Business Rules:** Cannot exceed invoice amount

## 1.3 Event Storming сессии

Провели 3 Event Storming сессии с участием:

- Разработчики (8 человек)
- Бизнес-аналитики (2 человека)
- Domain эксперты (менеджеры отделов)

## Результаты:

- 50+ бизнес-событий
- 20+ агрегатов
- 15+ bounded contexts
- 5+ process flows

# 📊 Результаты через 12 месяцев

## Качественные улучшения:

- Единый язык - разработчики, аналитики и бизнес говорят на одном языке
- Ясная архитектура - понятно где искать код для конкретной бизнес-функции
- Тестируемость - изолированная бизнес-логика, легко покрывается тестами
- Расширяемость - новые функции добавляются быстрее и безопаснее
- Документация - код самодокументируемый через domain concepts

# 🎓 Извлеченные уроки

## Что сработало хорошо:

- ✅ Постепенное внедрение - начали с одного bounded context
- ✅ Обучение команды - регулярные воркшопы и pair programming
- ✅ Event Storming - отличный инструмент для discovery phase
- ✅ Ubiquitous Language - фундамент для успеха
- ✅ Стратегия Strangler Fig - минимальный риск, быстрая отдача

## Что бы сделали иначе:

- Начали бы раньше с testing - тесты дают confidence для рефакторинга
- Больше вовлекли бы бизнес - domain эксперты критически важны
- Создали бы больше документации на ранних этапах
- Инвестировали бы в CI/CD с самого начала

## Советы для других команд:

- Не пытайтесь внедрить всё сразу - начинайте с маленького, но важного - контекста
- Инвестируйте в обучение - DDD требует смены mindset
- Работайте с бизнесом - без domain experts это бессмысленно
- Принимайте компромиссы - идеального DDD не бывает в legacy
- Измеряйте результаты - количественные метрики важны для бизнеса

# 🏆 Ключевые выводы

## Для технических лидов:

- DDD - это инвестиция с долгосрочной отдачей
- Начинайте с малого и масштабируйте постепенно
- Команда важнее технологий - обучайте и вовлекайте
- Измеряйте успех через метрики, а не ощущения

## Для бизнеса:

- Качество кода = скорость бизнеса - инвестиции окупаются
- Единый язык уменьшает misunderstandings
- Поддерживаемость снижает TCO (Total Cost of Ownership)
- Scalable команда = scalable бизнес

## Для разработчиков:

- DDD делает код понятнее
- Тестировать становится проще
- Меньше страха изменений
- Больше профессионального роста

---

_DDD - это не серебряная пуля, а мощный набор принципов и практик. В legacy проектах он особенно ценен, потому что помогает навести порядок в хаосе. Наш опыт показывает, что постепенное, системное внедрение DDD может трансформировать даже самый сложный legacy проект в современную, поддерживаемую систему._
